## App-Internal Secrets (Native Container Apps Secrets — No Key Vault)

> ⛔ **No Key Vault.** Container Apps store app-internal secrets in the app's **native** `secrets` array with a literal value supplied by an `@secure()` param at deploy time. NEVER use `keyVaultUrl`, `@Microsoft.KeyVault(...)`, or a Key Vault secret resource.
>
> ⛔ **Database, cache, storage, Cosmos, and queue access is managed-identity + token.** There is no connection-string password or access key to store, so those services contribute **no** secrets at all. The only values that belong here are genuinely app-internal (e.g. `SECRET_KEY`, a JWT signing key, a third-party API key).

```bicep
@secure()
param appSecretKey string

resource containerApp 'Microsoft.App/containerApps@2024-03-01' = {
  name: caName
  location: location
  tags: tags
  identity: { type: 'SystemAssigned' }
  properties: {
    managedEnvironmentId: env.id
    configuration: {
      ingress: { external: true, targetPort: 8000 }
      // Native CA secrets — literal value from an @secure() param. No keyVaultUrl.
      secrets: [
        { name: 'app-secret-key', value: appSecretKey }
      ]
    }
    template: {
      containers: [
        {
          name: appName
          image: containerImage
          env: [
            // App-internal secret via native secretRef
            { name: 'SECRET_KEY', secretRef: 'app-secret-key' }
            // Database via managed identity — plain connection params, NO password/secretRef:
            { name: 'PGHOST', value: pgHost }
            { name: 'PGDATABASE', value: dbName }
            { name: 'PGUSER', value: appMiName }
            { name: 'PGSSLMODE', value: 'require' }
          ]
        }
      ]
    }
  }
}
```

> ⛔ **Every `secretRef` MUST have a matching entry in the app's native `secrets[]` array.** A `secretRef` with no backing secret fails at revision creation. There is no Key Vault role assignment and no secret-seeding step — the value arrives as a deploy parameter.
