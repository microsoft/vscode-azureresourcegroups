# azure-deploy Overlay

Upstream ships **skills**. This extension ships a **custom agent**. This skill is the
reproducible transformation between the two, so an upstream refresh is a re-run instead of a
hand-merge.

```
.agents/skills/azure-app-onboard*     →  [overlay rules]  →  resources/agents/azure-deploy/**
   (vendored, NEVER edited)                                     (generated, NEVER hand-edited)
```

> ⛔ **The two hard invariants of this repo.**
> 1. **Never edit a vendored upstream file.** Fixes go into a rule here, not into `.agents/`.
> 2. **Never hand-edit the generated agent tree.** If you did, `apply` will overwrite it. Promote
>    the edit into a rule first (see [Capturing a new local change](#capturing-a-new-local-change)).

## Quick Reference

| | |

| Executable checks | [`checks.json`](checks.json), [`scripts/verify-overlay.ps1`](scripts/verify-overlay.ps1) |
| Upstream baseline | `baseline.json` — generated by [`scripts/capture-baseline.ps1`](scripts/capture-baseline.ps1) |

## Versioning model

The generated tree is **not** the source of truth and is never patched in place. The rules are the
source of truth; the tree is rebuilt from pristine upstream on every re-vendor. Regeneration is
safe because every rule is idempotent — replaying the full ruleset over an already-correct tree is
a no-op.

What *is* versioned is the relationship between the three moving parts:

| Artifact | Records | Where |
|---|---|---|
| Upstream baseline | sha256 per vendored upstream file at the last **verified** apply | `baseline.json` |
| Overlay fingerprint | one hash over every rule, snippet, check and script | `baseline.json`, and stamped into the tree |
| Provenance stamp | which ruleset built this tree, when, and what was left unanchored or manual | `<agent>/.overlay.json` |

The baseline exists to answer one question on the next upstream drop: *which of our rules are
anchored in text that moved?* Without it, a re-vendor means re-reading 84 files. With it, drift
names the handful of rules that need review.

⛔ The baseline advances **only** when every required check passes. `capture-baseline.ps1` runs
`verify-overlay.ps1` itself and refuses otherwise — a baseline captured over a failing tree
silently redefines broken output as the new known-good.

### Re-vendor sequence

```powershell
# 1. What moved underneath the rules? Read this BEFORE regenerating.
pwsh ./agent-overlay/scripts/drift-overlay.ps1 -UpstreamRoot ./.agents/skills

# 2. Rebuild. Treat every UNANCHORED line in the report as a stop condition.
pwsh ./agent-overlay/scripts/apply-overlay.ps1 -UpstreamRoot ./.agents/skills -OutRoot ./resources/agents -Force

# 3. Gate.
pwsh ./agent-overlay/scripts/verify-overlay.ps1 -AgentRoot ./resources/agents

# 4. Only once green: advance the baseline.
pwsh ./agent-overlay/scripts/capture-baseline.ps1 `
    -UpstreamRoot ./.agents/skills -AgentRoot ./resources/agents -UpstreamRef "<sha> (<upstream PR>)"
```

Step 1 predicts; step 2 confirms. A rule that drift flags as needing review but that apply does
**not** report `UNANCHORED` has survived the reword — the drift report is a superset by design.

## Modes

| Mode | Use when | Writes files? |
|---|---|---|
| `verify` | CI, or before touching anything — is the current tree overlay-conformant? | No |
| `drift` | New upstream drop landed — what changed underneath our rules? | No |
| `apply` | Regenerate the agent tree from vendored upstream + rules | Yes |
| `capture` | A local fix was hand-made and must become a durable rule | Yes (rules only) |

Default to `verify` when the user is vague. Never run `apply` without showing the drift report
first — a silent regeneration can drop a rule that upstream has since made unanchorable.

Each rule is **semantic and idempotent**: it declares an anchor, an operation, an idempotency key,
and a verification assertion. Rules never reference line numbers — upstream reflows constantly.

## Workflow

### Step 1 — Establish the baseline

Read `baseline.json`. It records, per upstream file, the SHA-256 captured at the last successful
`apply`. Recompute hashes for the current vendored tree and classify every file:

| Classification | Meaning | Action |
|---|---|---|
| `unchanged` | hash matches baseline | Replay rules, no review needed |
| `changed` | upstream edited it | Replay rules, then ⛔ **re-anchor review** (Step 4) |
| `added` | new upstream file | Route per `import-map.json.routing`; flag if unmapped |
| `removed` | upstream deleted it | ⛔ Stop. A rule may target a file that no longer exists |
| `overlay-only` | listed in `import-map.json.overlayOnly` | Never overwritten by upstream |

### Step 2 — Copy the mapped tree

Apply `import-map.json.routing` to produce the destination tree. This is a pure move/rename —
**no content edits in this step**. Do not invent destinations: an upstream file with no routing
entry is an error, not a judgement call.

### Step 3 — Replay rules in ascending ID order

Run every rule in `rules/`, lowest ID first (packaging before everything, because later rules
reference `instructions.md` paths that only exist after `100` runs).

For each rule:

1. Locate the **anchor**. If absent → record `UNANCHORED`, do not guess a location.
2. Check the **idempotency key**. If present → skip; the rule already applied.
3. Apply the **operation**.
4. Evaluate the **verification assertion**.

⛔ **An `UNANCHORED` rule is a stop condition, not a warning.** It means upstream restructured the
text the rule depends on. Surface it to the user with the rule ID, the missing anchor, and the
upstream file — then let a human decide whether to re-anchor the rule or drop it because upstream
now does it natively.

### Step 4 — Re-anchor review (only for `changed` upstream files)

For each upstream file classified `changed`, diff old vs new upstream content and ask, per rule
targeting that file:

- Did upstream **adopt** our behavior? → Delete the rule; note it in the run report. Keeping it
  produces duplicated, contradictory guidance.
- Did upstream **contradict** our behavior? → Keep the rule, and record the conflict. Our policy
  wins for CoR, but the divergence is now deliberate and documented.
- Did upstream **move** the anchor? → Update the rule's anchor only. Never weaken the assertion to
  make a check pass.

### Step 5 — Verify

```powershell
pwsh ./agent-overlay/scripts/verify-overlay.ps1 -AgentRoot ./resources/agents
```

The script executes [`checks.json`](checks.json). Every `required` check must pass before the run
is reportable as successful. A failing check means the generated tree is not deployable — do not
describe the import as complete.

### Step 6 — Report

Report per category: rules applied, rules skipped (already idempotent), rules `UNANCHORED`,
upstream files `changed`/`added`/`removed`, and the check summary. Then advance the baseline via
`capture-baseline.ps1` — **only if every required check passed**.

## Capturing a new local change

When someone fixes agent behavior by editing the generated tree directly, that fix dies at the next
re-vendor. Convert it:

1. Identify the destination file and its upstream origin via `import-map.json`.
2. Confirm the change is genuinely **ours** — not an upstream bug that should be reported upstream
   instead. Overlay rules are for productization deltas, not for patching upstream defects
   indefinitely.
3. Pick the category file by intent, and allocate the next free ID in that range.
4. Write the rule with all five fields (anchor, operation, idempotency key, content, verification).
5. Add a matching entry to `checks.json`.
6. Re-run `apply` from pristine upstream and confirm the hand-edit is reproduced exactly.

Step 6 is the whole point. A rule that cannot regenerate the edit from a clean checkout is not a
rule, it is a comment.

## Known limits of this mockup

- Rule application is agent-performed, not a deterministic transform. Verification is the
  guardrail; treat a green `verify` run as the source of truth, not the agent's own narration.
- `checks.json` asserts presence/absence of policy markers. It proves a policy is *stated*, not
  that the surrounding prose still reads coherently after an upstream reflow. Step 4 is still a
  human read.
- Baseline hashing detects that upstream changed a file, not whether the change is semantically
  relevant to our rules.
